# Architecture decisions

Short records of the decisions that shape the code base. Each one says what was decided, why, and what it costs. New decisions are added at the end with the next number.

??? success "ADR-1 · Firebase as the whole backend"
    **Decision.** Firebase Auth and Cloud Firestore are the only backend. No custom server, no separate local database.

    **Why.** Free tier, managed auth, and Firestore's built-in offline persistence gives offline-first behaviour without a second storage layer.

    **Trade-offs.** Vendor lock-in; the app can't run without Firebase config; security lives in `firestore.rules`, which must be deployed separately.

??? success "ADR-2 · Feature folders with data / domain / presentation layers"
    **Decision.** Code is grouped by feature, and each feature splits into data, domain and presentation. Repositories are interfaces in the domain layer; implementations in the data layer.

    **Why.** The UI and the bloc never depend on Firebase, so they can be tested with in-memory fakes, and Firebase can change without touching screens.

    **Trade-offs.** More files per feature than a flat structure.

??? success "ADR-3 · flutter_bloc for state, Either for errors"
    **Decision.** Business logic lives in blocs (`WorkoutBloc`); repositories return `Either<Failure, T>` from `dartz` instead of throwing.

    **Why.** Predictable event → state flow that is easy to unit test; errors are values the bloc must handle.

    **Trade-offs.** Some boilerplate per event.

??? success "ADR-4 · Freezed and json_serializable, generated code committed"
    **Decision.** Entities, events and states use Freezed; Firestore models use `json_serializable`. Generated files are committed.

    **Why.** No hand-written `copyWith`, equality or JSON code; builds don't need a generation step.

    **Trade-offs.** Generated code must be regenerated by hand after model or generator changes; CI doesn't check it.

??? success "ADR-5 · get_it service locator"
    **Decision.** Dependencies are registered in `lib/injection_container.dart` and resolved through `sl`.

    **Why.** Tests replace Firebase-backed repositories with fakes in one call (`registerFakeDependencies`) and still run the real `MainApp`.

    **Trade-offs.** Dependencies are resolved at runtime, so a missing registration is a runtime error rather than a compile error.

??? success "ADR-6 · Golden screenshot tests as the visual standard"
    **Decision.** Every screen has a golden PNG in `test/goldens/screens/`, rendered at phone size with bundled fonts; CI fails when a screen changes without an updated golden.

    **Why.** Visual changes are reviewable in the pull request (before/after comment) and accidental UI regressions are caught. The same PNGs illustrate this documentation.

    **Trade-offs.** Goldens must be updated deliberately with every UI change; they are rendered by the Flutter test engine, not a real device (the emulator workflow covers that).

??? success "ADR-7 · Documentation in the repository, published with MkDocs"
    **Decision.** Documentation is Markdown in `docs/`, built with MkDocs Material and deployed to GitHub Pages by Actions.

    **Why.** Docs change in the same pull request as the code they describe and go through review and CI. A GitHub Wiki is a separate git repository without pull requests or CI.

    **Trade-offs.** GitHub Pages must be enabled once in repository settings.
